# 面试讲解：先把这五件事讲清楚

## 1. 一分钟介绍

“我用 Python 标准库从零写了一个最小 Agent。用户发来问题后，我把上下文和四个工具的 Schema 发送给真实 LLM。模型可以直接回答，也可以返回工具调用。程序校验参数、执行工具，把结果交回模型，再决定继续还是结束。最多循环六次，防止一直运行。每个用户的每个窗口独立保存会话，所以支持重启后继续聊。”

真实 API 是否已经执行成功，请以 `TEST_REPORT.md` 为准。当前默认使用 Groq 免费套餐的 Qwen 模型；题目没有指定厂商或要求付费。配置可用密钥并验证后再演示，不能把单元测试替身说成真实模型。

## 2. “它与普通聊天有什么区别？”

普通聊天通常是问一次、答一次。Agent 能实际调用函数。例如“查天气，再记待办”需要模型先选择工具，程序得到天气数据或写入待办，再让模型根据执行结果组织答案。有没有工具调用，取决于模型返回的结构化内容。

## 3. “这个循环怎么写的？”

打开 `mini_agent/runtime.py`，找到 `for step in range(...)`：

```text
循环最多六次：
    拼好上下文，调用模型
    解析模型输出
    如果有最终答案：退出
    如果有工具调用：校验参数并执行
    把工具结果加到上下文
```

最容易漏掉的是最后一步：**工具不是执行完就结束，结果还要交回模型**。比如算出 60 后，“再除以 4”依赖之前结果；如果不保存结果，模型就没有可靠依据。

本项目采用原生 function calling，没有用关键词判断代替模型选工具。输出里的 `reason` 只是简短行动说明，真正决定工具调用的是 `tool_calls`。

## 4. “同一个用户开两个窗口为什么不会串？”

不能只用用户 ID 存历史，还要有 session ID。A/window1 和 A/window2 是两份状态，B/window1 也是另一份。SQLite 文件分别存放；待办、摘要、最近工具结果也都保存在对应会话内。

这里的用户标识只是本机演示用，不是登录认证。相同会话同时发送两条消息时，数据库锁避免后一个覆盖前一个；不同会话独立执行。

## 5. “memory 什么时候拿出来，放哪里？”

每次收到消息先读这个会话的 memory；每次调用模型前再拼一次 context。顺序是固定规则、记忆数据、最近几轮历史、当前问题及本轮工具结果；工具 Schema 另放在 API 的 tools 字段。

“刚才那个计算结果”靠最近历史和最近工具结果；“我的待办”靠完整待办状态；老的闲聊会压成摘要。摘要有损，不能保证一直记住每一个细节。

只按完整对话轮次压缩，是因为 assistant 的工具调用必须和相应 tool 结果配对。拆散会导致 API 消息结构出错。

## 常见追问

**为什么不用框架？** 题目要求自己实现 Runtime，而且小项目直接用一个循环更容易解释。

**怎么新增工具？** 写一个接受 args 和 state 的 Python 函数，再把名称、描述、参数 Schema 和函数注册进去。主循环不变。

**工具参数错了怎么办？** 执行前校验，失败返回结构化错误，交给模型修正；修正仍然占用轮次预算。

**调用 API 超时怎么办？** 有 30 秒超时和最多一次重试，失败明确提示；本次已经完成的本地待办在正常错误退出时会保留。

**为什么计算器不用 eval？** eval 会执行 Python 代码，而这个工具只应该计算数字。AST 白名单只接受有限算术表达式。

**测试是不是假的？** 单元测试用固定模型输出来稳定验证程序；真实 API 冒烟测试另外验证模型是否按 Schema 自主调用工具。两种验证不能互相替代。

**还有哪些限制？** 搜索和天气是 mock，摘要有损，没有生产登录鉴权；没有远程副作用工具和复杂恢复机制。这些都是为了符合“最小可用、容易理解”的范围。

## 建议现场演示顺序

1. 先打招呼，展示直接回答。
2. 算 `(12+8)*3`，再追问“结果除以 4”，展示工具循环与记忆。
3. 窗口 1 查模拟天气并记录“带伞”，窗口 2 搜索周报并记录“写周报”。
4. 分别列待办，展示隔离；退出再打开同一会话，展示持久化。
5. 展示一段 trace 和测试结果，说明错误处理和边界。
