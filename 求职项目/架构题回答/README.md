# 架构题回答

[下载 Word 原文件](架构题回答.docx?raw=true) · [返回本次面试提交入口](../../README.md)

以下为 Word 原文的在线阅读版，仅调整显示格式，未改写问答内容。原始 Word 文件按字节保留。本文件是架构设计问答，不代表最小 Agent 已实现其中讨论的全部能力。

## 1. 一个 Session 连续聊了 200 轮，Context 快爆了。怎么压缩？怎么保证继续聊得流畅？

我会采用远的总结，近的原文，关键事实结构化的思想。我不会简单截掉前面的消息，而会采用‘最近对话 + 历史摘要 + 结构化关键状态’的方式压缩。最近几轮保留原文，较早内容做滚动 Summary，同时把用户目标、重要事实、已经做出的决定、未完成事项、关键 ID 和约束单独结构化保存。每次摘要更新时不是重新总结全部200轮，而是在旧 Summary 基础上增量更新。模型调用时组合 System Prompt、Summary、关键 State 和最近几轮对话，这样既降低 Token，又保持上下文连续。

## 2. 和聊天 Agent 熟悉半个月后，用户又问了以前问过的问题，Memory 怎么召回更合理？

我会采用不是找“所有过去”，而是找“现在最相关的过去”的思想。我不会把半个月所有聊天全部塞进 Context，而是根据当前 Query，从长期 Memory 中按相关性、时间新鲜度、重要性和用户 Scope 做检索。优先召回和当前问题直接相关的历史结论、用户偏好和上次任务结果，再和当前 Context 合并。如果旧 Memory 和用户当前明确表达冲突，以当前指令为准。

## 3. 用户让 Agent 每天早上 9 点根据昨天聊天情况做复盘总结，怎么设计？

我会把它设计成定时任务。Scheduler 每天9点生成一个 task_id，按用户时区读取昨天0点到24点的聊天记录，先筛选有效内容，再做聚合和总结，最后把结果保存并发送给用户。整个任务需要幂等，防止重试时一天生成两份复盘。

## 4. Agent 有同步和异步工具。异步工具不能让用户一直等，但结果仍然重要，怎么设计？

对于耗时异步 Tool，我不会让一次 HTTP 或 Agent Turn 一直挂着等待，而是提交任务后立即返回 task_id，把任务放到任务的队列中，由后台 Worker 执行，并持久化任务的状态。用户可以继续聊天或查询任务状态；任务完成后通过 SSE、WebSocket、Push 或站内通知告知用户，如果后续 Agent 决策必须依赖该结果，就在等待点保存 Checkpoint，结果回来后恢复状态再继续执行。

## 5. Claude Code 的工具输出方式，和 GLM / 豆包等 OpenAI-compatible Function Calling 有什么不同？各自优缺点？

Claude 的 Tool Use 更偏 Content Block 模型，tool_use 和 tool_result 都嵌在消息内容中，表达能力和 Agent 轨迹组合更灵活；OpenAI-compatible 通常使用 tool_calls + role=tool，结构更标准化，最大的优势是生态兼容和多模型切换方便。Claude 风格更适合丰富 Agent 交互，但适配成本更高；OpenAI-compatible 更通用，但不同厂商只是接口兼容，具体能力和细节仍需要做 Provider Adapter。
